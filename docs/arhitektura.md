# Архитектура

Решење је модуларни монолит са јасним границама одговорности.

```text
Api ──────────> Application <──────── Infrastructure
 │                  ▲
 ├────> Security ───┤
 ├────> Protocols ──┤
 ├────> Simulation ─┘
 └────> Domain <──── Application
```

`Domain` не зависи од других пројеката. `Application` зависи само од домена и дефинише уговоре за складиштење. `Infrastructure` имплементира складишта. `Security` садржи контролу приступа, надзор команди и синтетичке сценарије. `Protocols` представља виртуелне регистре и опциони read-only Modbus TCP сервер. `Simulation` покреће периодичну физичку симулацију и монитор инцидената. `Api` је композициони корен.

## Главни токови

1. `SimulationService` периодично позива `PlantService.Advance`.
2. `Plant` мења ниво резервоара и примењује заштиту од преливања.
3. `PlantService` бележи узорке телеметрије и алармне догађаје.
4. `IncidentMonitorService` претвара релевантне догађаје у инциденте.
5. API и контролна табла читају стање преко сервиса; команде проверавају улогу.

## Одлуке

- Без непотребних generic repository и mediator слојева.
- Интерфејси се користе тамо где постоје стварне инфраструктурне варијанте.
- Тестови су груписани искључиво у `Tests/`.
- Све физичке вредности су симулиране.
- Modbus TCP се по подразумеваном подешавању не покреће и не прихвата команде за упис.

## Позната техничка ограничења

Синхрони упис у PostgreSQL из периодичне симулације није погодан за велики проток. Инциденти нису трајни. Дељени API кључеви не представљају индивидуалне кориснике. Нема аутоматизованих миграција, OPC UA интеграције, распоређеног система или продукционог TLS termination слоја. Ове могућности захтевају засебне фазе имплементације и тестирања.
